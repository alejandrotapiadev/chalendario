MVP DE UN CALENDARIO PERSONAL

Para un MVP de calendario personal, conviene mantener el producto pequeño, pero diseñarlo desde el principio para que añadir recurrencias, sincronización, colaboración y recordatorios no obligue a rehacer el modelo de datos.

La clave para este proyecto es separar dos conceptos:

1. Control de versiones del proyecto: Git desde el día 1.
2. Historial de cambios de los eventos: también diseñarlo desde el inicio, aunque la interfaz para ver versiones anteriores pueda llegar después.


1. QUÉ DEBERÍA TENER EL MVP

CALENDARIO
- Vista mensual.
- Vista semanal.
- Vista diaria.
- Navegación entre fechas.
- Botón "hoy".

EVENTOS

Un evento puede tener como mínimo:

id
calendar_id
title
description
start_at
end_at
timezone
all_day
location
status
created_at
updated_at

Operaciones:
- crear
- editar
- eliminar
- mover/redimensionar
- eventos de todo el día
- descripción
- ubicación
- colores o categorías

No metería todavía reuniones con participantes, videollamadas, invitaciones, disponibilidad, etc.


RECORDATORIOS

Modelo sencillo:

event_reminders
- id
- event_id
- minutes_before
- channel

Ejemplos:
- 30 minutos antes
- 10 minutos antes

Se puede empezar con notificaciones dentro de la aplicación.


RECURRENCIA

Una aplicación de calendario sin recurrencias se siente limitada, pero una implementación completa puede ser bastante compleja.

Para empezar:
- diario
- semanal
- mensual

Para una fase posterior:
- "cada segundo martes"
- excepciones
- series parcialmente modificadas
- reglas RRULE complejas


2. CONTROL DE VERSIONES DE EVENTOS

Si el versionado es una característica importante, no conviene sobrescribir simplemente un evento en la base de datos.

Ejemplo:

Estado inicial:
Lunes 10:00
"Gym"

Después:
Lunes 11:00
"Gym"

En vez de perder el estado anterior:

Version 1
title = Gym
start = 10:00

Version 2
title = Gym
start = 11:00

Así se puede reconstruir el estado del evento en cualquier momento.


MODELO SENCILLO

Tabla principal:

events
- id
- current_version
- created_at
- updated_at

Historial:

event_versions
- id
- event_id
- version
- title
- description
- start_at
- end_at
- timezone
- all_day
- location
- status
- created_at
- created_by
- change_reason

Relación conceptual:

event
  |
  ├── version 1
  ├── version 2
  ├── version 3
  └── version 4 <- actual

Esto permite:
- historial
- deshacer
- recuperar una versión anterior
- saber qué cambió
- auditoría
- sincronización futura
- gestión de conflictos de edición

Para un calendario personal no hace falta convertir todo el sistema en Event Sourcing. Empezaría con:

"Estado actual + historial de versiones inmutables."

Es una arquitectura más sencilla de entender y mantener.


3. MOSTRAR QUÉ CAMBIÓ

Además de guardar snapshots completos, más adelante se puede guardar qué campos cambiaron.

Ejemplo conceptual:

version = 7

changes:
{
  "start_at": {
    "from": "2026-09-21T10:00",
    "to": "2026-09-21T11:00"
  }
}

Esto permitiría mostrar:

"Se cambió la hora de 10:00 a 11:00."

No es imprescindible para el MVP, pero es una buena evolución.


4. ARQUITECTURA

Para un proyecto nuevo:

Frontend
   |
   v
API
   |
   ├── Auth
   ├── Calendar
   ├── Events
   ├── Reminders
   └── Versioning
           |
           v
       PostgreSQL

No empezaría con microservicios.

Una arquitectura razonable sería:

- Monolito modular
- PostgreSQL
- Redis solo cuando haga falta
- Un worker para notificaciones/tareas

Separación lógica:

/modules
    /auth
    /calendars
    /events
    /recurrence
    /reminders
    /versioning

Aunque todo se ejecute como una sola aplicación.


5. MODELAR BIEN LOS EVENTOS

Hay una decisión importante: no mezclar "evento" y "ocurrencia".

Ejemplo:

"Entrenamiento todos los lunes a las 18:00."

Eso no son realmente cientos de eventos independientes. Es una serie con múltiples ocurrencias.

A futuro se puede modelar como:

event_series
- id
- title
- recurrence_rule
- timezone
- ...

event_occurrences
- id
- series_id
- start_at
- end_at
- status
- ...

Para el MVP se puede simplificar y usar:

events
- id
- series_id nullable
- ...

Lo importante es no acabar tratando una recurrencia como cientos de registros completamente independientes sin una estructura clara.


6. GIT DESDE EL PRIMER DÍA

Para un proyecto individual no hace falta una estrategia de ramas complicada.

Puede bastar con:

main
feature/*

También podría usarse develop, pero no es imprescindible.

Conviene hacer commits pequeños y descriptivos.

Mejor:

feat: add event creation
feat: add event update
feat: add event version history
test: add event version tests
fix: handle timezone conversion

que algo genérico como:

"Implementación calendario"

Se puede usar Conventional Commits para mantener el historial limpio y generar changelogs más adelante.


7. VERSIONAR TAMBIÉN LA BASE DE DATOS

Es muy importante usar migraciones.

Por ejemplo:

migrations/
    001_create_users
    002_create_calendars
    003_create_events
    004_create_event_versions
    005_add_reminders

Así el esquema de la base de datos queda reproducible.

La idea es que, partiendo de una base de datos vacía, ejecutar las migraciones produzca exactamente el esquema esperado.

9. DOCUMENTAR DECISIONES DE ARQUITECTURA

Dentro de docs/ conviene tener:

architecture.md
data-model.md
decisions/
    001-use-postgresql.md
    002-event-versioning.md

Es útil usar ADRs (Architecture Decision Records).

Ejemplo:

ADR-002: Versionado de eventos

Contexto:
Los eventos pueden modificarse y necesitamos conservar su historial.

Decisión:
Mantener el estado actual del evento y snapshots inmutables
por cada modificación.

Consecuencias:
+ historial completo
+ rollback sencillo
+ auditoría
- más almacenamiento

Esto ayuda mucho cuando el proyecto crece y ya no recuerdas por qué tomaste una decisión técnica.

13. DECISIÓN CLAVE

Antes de programar, conviene definir esta regla:

"Cada modificación de un evento crea una nueva versión; las versiones nunca se modifican."

Ejemplo:

Event #42

v1
├─ title: Dentista
├─ start: 09:00
└─ location: Madrid

v2
├─ title: Dentista
├─ start: 10:00
└─ location: Madrid

v3
├─ title: Dentista
├─ start: 10:00
└─ location: Alcobendas

El evento actual apunta a v3.

Esto facilita características futuras como:
- undo
- historial
- recuperación
- auditoría


IDEA PRINCIPAL

No conviene diseñar el MVP pensando solo en las pantallas.

Primero hay que diseñar bien el modelo de dominio y, especialmente, definir qué significa "cambiar un evento".

En un calendario, esa decisión condiciona buena parte de la arquitectura futura.
